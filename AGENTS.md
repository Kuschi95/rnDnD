# rnDnD

Expo rewrite of Niko's Kotlin D&D session app. The Kotlin project is the functional spec, not code to port. The full analysis is `docs/DndApp-Analyse.md`.

## Expo has changed — do not trust training data

Read the major version of `expo` in `package.json`, then fetch `https://docs.expo.dev/versions/v<major>.0.0/` before using an Expo, EAS, or React Native API. For everything else, start at `https://docs.expo.dev/llms.txt`. Project skills under `.agents/skills` are the Expo agent skills (all of them except `expo-skill-feedback`). Load the one that matches the task. `expo-overview` is the entry point.

`ios/` and `android/` are generated by prebuild. Do not commit or hand-edit them. Configure native behavior in `app.config.ts`.

Install libraries with `npx expo install <package>` so the version matches SDK 58.

## Stack

- Expo SDK 58, managed workflow, TypeScript strict, Expo Router under `src/app`.
- React Native Paper (Material 3) with one parchment theme in `src/theme/theme.ts`. The Kotlin app mixed Material 2 and Material 3. Do not add a second UI kit.
- Firebase JS SDK (`firebase/auth`, `firebase/firestore`) for project `dndniko-4de7a`, so the app can run in Expo Go. Config is `EXPO_PUBLIC_*` in `.env`. There is no `firebase/compat` and no `expo-firebase-analytics`.
- Drizzle ORM on `expo-sqlite`. Migrations in `drizzle/` run at startup through `applyMigrations` (`execAsync`, not Drizzle's `useMigrations`).
- Jest (`jest-expo`), ESLint (`eslint-config-expo`), Prettier.

SDK 58 Expo Go was not in the stores when this repo was created. A development build is the fallback until it is. See the README.

`@/*` maps to `src/*`. Colocate tests next to the module (`*.test.ts`).

Route groups:

| Route                             | What the placeholder stands for                               |
| --------------------------------- | ------------------------------------------------------------- |
| `(auth)/login`, `(auth)/register` | Email and password. These forms call Firebase.                |
| `(home)`                          | Host a lobby or join with a code.                             |
| `lobby/[code]`                    | Lobby, then the countdown handoff.                            |
| `dm/[code]`                       | Drawer: party, monsters/NPCs, chat, notes, compendium.        |
| `player/[code]`                   | Drawer: sheet, inventory, abilities, armour, monsters, notes. |

The root layout protects everything except `(auth)` with `Stack.Protected`. Duplicate Kotlin stack routes (`inventory_screen`, `abilities_screen`, `notes_screen`, `player_notes_screen`, `npc_screen`) stay collapsed into the player drawer.

## Firebase, and the later native switch

`src/firebase/client.ts` is the Auth entry. `src/firebase/firestore.ts` is the Firestore entry. Other modules import those, not `firebase/*`.

Auth persistence is AsyncStorage via `getReactNativePersistence` on Android and iOS, and `browserLocalPersistence` on web. Firebase JS SDK 13 does not put a `react-native` condition on the `firebase/auth` and `firebase/firestore` export maps, so `metro.config.js` aliases those two imports to the React Native builds for non-web platforms.

When offline cache matters for a real table test, switch Auth and Firestore to `@react-native-firebase` in an EAS dev client:

1. Add `expo-dev-client` and the `@react-native-firebase/app`, `auth`, and `firestore` config plugins in `app.config.ts`.
2. Register an iOS app in the same Firebase project. The JS SDK does not need `GoogleService-Info.plist`; the native SDK does.
3. Replace `src/firebase/client.ts` and `src/firebase/firestore.ts`.
4. Remove the JS Firestore client in the same change. Do not ship both.

Do not add `@react-native-firebase` while developing in Expo Go. Analytics can wait. If it is added, use `@react-native-firebase/analytics` in that dev client.

## Data

Local tables mirror the Firestore documents. Nested character fields (`secondaryAttributes`, `playerClass`, `abilities`, `inventory`, `notes`) are JSON columns. Lobby monsters are one JSON document per NPC because the stat block is a single Firestore document. Column names that Kotlin already writes stay as they are: `lastUpdatedBy`, `itemRes`, `haltbarkeitsValue`, `armorRating`, `pastHistory`, `userId`. Chat `timestamp` is an epoch-millis **string**.

`sync_outbox` is local only. Repositories write SQLite and enqueue a Firestore-shaped payload. `src/sync/sync-engine.ts` pushes that queue and can subscribe to remote snapshots. Screens are not wired to it yet. Reads are local-first: a screen reads the repositories, not Firestore. Remote snapshots skip a document that still has an outbox row. Listeners return an unsubscribe function; call it on blur.

`notes` is stored as a JSON array. The analysis describes the Kotlin type as `PlayerNotes`. Confirm a live document before the first write from this app.

`members` is copied unchanged. The Kotlin app stores the host uid and player character ids in the same array. Do not "fix" that inside a normal write. It needs a one-time repair, then both clients must agree. Prefer `host` as a uid and `members` as character ids.

Lobby codes are the document ids (`lobbies/{code}`), not a field on the document.

## Rules and indexes

`firestore.rules` restricts characters, lobbies, monsters, and chats as described in section 10 of the analysis. `firestore.indexes.json` has the three chat composite indexes (`senderId` + `receiverId` + `timestamp`, `senderId` + `receiverId` + `read`, `receiverId` + `senderId` + `timestamp`). Do not deploy either file until the `members` repair is decided. The rules file says why: a DM read of someone else's character cannot be expressed until the character points at a lobby.

## Icons and compendium

`src/icons/icon-map.ts` is keyed by drawable entry names. `class_rouge` is the only name the analysis quotes. The DndApp repo was not readable from the machine that scaffolded this project, so `assets/data/` does not yet contain `monster.json`, `spells.json`, or `monster_lore.json`. Leave `monster_lore_sources.json` out until a screen needs it. When the JSON arrives, load it with `expo-asset` or `expo-file-system`. Do not `import` the multi-megabyte files into a route module.

Converting the 434 vector drawables is a TODO in the icon map. Do not rename keys.

## Do not copy from the Kotlin client

- `viewModel()` plus a second `viewModel()` on the same screen. One store per route, destroyed on blur.
- Snapshot listeners that are never removed.
- `joinLobby` that does not add a member. Membership has to be an explicit write.
- Rejoin navigation that drops `hostUserId`.
- The dead `updatedBy` read. Writers use `lastUpdatedBy`.
- `firebase/compat`, callback-style tasks, Room, Coil, Gson, and the unused `SketchScreen`.
- A second Firebase project, Google sign-in, or system push. Push is out of scope until the in-app listener matches.

## Migration order

1. This foundation: Expo Router groups, EAS profiles, icon-map module.
2. Deploy rules and chat indexes only after the `members` repair, and confirm the Kotlin client still reads the documents.
3. Auth is already on the JS SDK, including sign-out and password reset. Move to `@react-native-firebase/auth` only when leaving Expo Go.
4. Character read and write, including the creation wizard and the player sheet. This proves the icon map.
5. Lobby create, join, rejoin, member listener, countdown, then DM versus player.
6. DM drawer: party, NPC CRUD, compendium, DM notes.
7. Player drawer: inventory, abilities, armour, notes, monster view, DM-edit snackbar.
8. Private chat and unread state, after the indexes exist.
9. EAS production builds. `expo-notifications` only if background push is actually required.
